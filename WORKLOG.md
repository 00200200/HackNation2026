## Now (snapshot, edit in place)

Updated: 2026-11-22, by Claude workflow (#18 review fixes: full-run JSON committed, description and deck, for Michał).

**Works end to end:** web form (nginx, `frontend/`) → `POST /api/checks` (FastAPI, `prawdowid/app.py`) →
`verify()` (`prawdowid/verifier.py`) → PydanticAI agent on Claude splits the text into claims marked checkable or
not → each checkable claim runs Fact Check, EUvsDisinfo, the www.gov.pl site search, web search and the evidence corpus in parallel, then rerank and judge, verdict set in code (`prawdowid/pipeline.py`); non-checkable claims are
`nie podlega weryfikacji`. Without keys every outside source fails: the answer is a technical error ("Nie mogę teraz sprawdzić ..."), never a verdict (#60), unless the evidence corpus settles the claim; a claim whose Fact Check or web search was down and whose other evidence is not enough is `nie sprawdzono`, not `brak wystarczających dowodów`. Defaults since #63: check budget 40 s, 3 claims checked in full. Links (#4, on `main` as #28): fetched safely (`prawdowid/link.py`), main text goes through the same `verify()`; blocked pages, paywalls (incl. inline sign-in or subscribe walls), social media, URLs with a login or password, private addresses and non-HTML/PDF files return `cannot_check` with a request to paste the text. Each check is kept as one masked record in the check log (#17); each link check logs URL (secret query values, userinfo and fragment redacted, also in the answer), content hash, claims and result to stdout.

**Evidence corpus** (on `main` since #49, searched in every check since #74): `make corpus`
rebuilds `corpus/evidence.jsonl` from the audited source list `corpus/catalog.yaml` (robots.txt respected, 1 request/s per
domain, page cache in `corpus/.cache/`). Build of 21.11: 1,158 records from 11 registered domains, official (gov.pl,
CERT, Policja, Sejm ELI, IMGW, EU Official Journal, Odyseusz, GUS, SOK) and one fact-checker feed (Pravda, 15), 5.3 MB.
Demagog is not a direct source of the corpus (decision 21.11): its ratings come as ClaimReview records through Google
Fact Check Tools, and web search shows its search snippets (#76, decision 22.11). Odyseusz has 239 country profiles with the current MSZ notice and warning level.
`make corpus-check` checks the brief's thresholds; `tests/test_corpus_build.py` checks the committed file. Sources,
licences and limits: `docs/corpus.md`. Google Fact Check and EUvsDisinfo collectors are built but skipped until the
keys are in `.env`. Every check searches the corpus with BM25 in memory (`prawdowid/corpus_bm25.py`, `bm25s`; no
database, no model): the API builds the index at startup (0.7 s on a laptop), a lookup takes 0.6 ms (median).

## Decisions

- 2026-11-22: A fact-checker's verdict in its own words is its rating, and its data gap decides (ADR 0001 section 3). A verdict sentence ("…oceniamy jako fałsz", "…uznajemy za nieweryfikowalną") that the judge marks as the fact-checker's own conclusion counts like a ClaimReview rating; a fact-checker's Nieweryfikowalne or own data-gap conclusion gives `brak wystarczających dowodów` unless another fact-checker, or a reliable source published after it, takes a side. Reason: the round-4 full run (af7ec13) fell to abstention 0.75 (FC-D01, FC-D02, FC-D03: Konkret24 snippets from the new fact-checker search named a missing context, or older official snippets confirmed, against Demagog's "nieweryfikowalne") and missed FC-E03 and C02 (Demagog's "oceniamy jako fałsz/manipulację" on pages without markup). A rule that a fact-checker's plain "false" outranks another publisher's missing context was rejected: it would turn scenario B answers (old footage, the second fact-checker naming the year) into `fałszywe`.
- 2026-11-22: Moderator cases (#79, brief sections 2 and 5, scenario H). A check goes to the moderator queue when a checked claim ends `brak wystarczających dowodów` (never `nie sprawdzono`: an outage is no question without sources), when it logged a security event, or when a claim on a high-risk topic (evacuation or RCB alert, health emergency, elections, mobilisation; `cases.HIGH_RISK`, a guess) ended false, misleading or without enough evidence. Similar claims share a case (Jaccard ≥ 0.5 over the corpus search's stems, not tuned). Storage: a JSONL file next to the check log, same retention and session deletion; no database (the stdlib `sqlite3` would also fit; kept the check log's pattern). The answer names the case only after the write. Who receives cases: whoever the administrator gives `PRAWDOWID_ADMIN_TOKEN`, through `GET /api/cases`; nobody is notified otherwise. Without the token nothing is filed: a queue nobody can read is no hand-off (brief section 5).
- 2026-11-22: A search snippet cannot confirm a claim on its own (#127, ADR 0001 section 3). This refines Michał's 22.11 snippet decision below (#95, #76): snippets are still shown and labelled "fragment z wyników wyszukiwarki", never stored, and still refute, add context or stand in a conflict like a page of their type; a fact-checker's own conclusion in a snippet still confirms alone, any other snippet needs a second independent origin, and the answer says why (`judge.SNIPPET_ALONE`, in place of the generic `NOT_ENOUGH`). Same change: a fact-checker's rating is also read from the ClaimReview markup of its review page (a Fact Check hit for the same page wins), looked up with diacritics folded, "Częściowy fałsz" and "Partly false" mean `wprowadzające w błąd`, the newest of one publisher's same-claim ratings counts (two publishers that disagree stay a conflict), and a missing context on a `context` label counts only from a fact-checker or a document that also supports or refutes. The #127 plan marked the snippet rule as needing Michał's OK; his OK is UNCONFIRMED in this clone.
- 2026-11-22: An outage is never a verdict (#60, brief section 5 and scenario J). Only a provider failure counts (`WebSearch.failed`; zero hits and unreadable pages are answers). A claim is `nie sprawdzono` with the outage as the reason when Fact Check, every web query, or (for a government claim) the gov.pl search failed and the evidence found is not enough; when every checkable claim ended that way, the answer is `technical_error`. Evidence that decides a verdict still stands when another source is down. The eval fault switch (`X-Eval-Fault` with `X-Eval-Token`) works only for requests carrying the server's `PRAWDOWID_EVAL_TOKEN`, and such a request neither reads nor fills the result cache (#59). Defaults for long pages (#63): check budget 25 → 40 s (the API gives up at 60 s), claims checked in full 5 → 3; both UNCONFIRMED guesses, not measured live. Supersedes the 25 s in the "Time budget (#11)" entry below.
- 2026-11-22: **Michał's decision** (~01:00, relayed by the coordinator session FejkCzyFakt) (#95, #76): for fact-checkers and other sites that block the server (403), use the search provider's snippet, labelled "fragment z wyników wyszukiwarki" with the reason, never fetching around the block and never storing full text. As built (coordinator's brief): when our own fetch cannot use an allowlisted page (403/429 or another 4xx except 401/402, 5xx or no answer after the retry, unreadable robots.txt, over 8 s, over 2 MB, other type, no text), the hit stays as evidence built only from what Tavily returned (title and `content`), marked `snippet_only` with the reason; nothing more is fetched for it (no retry, no other user agent, no `raw_content`) and it is never saved. A login or payment wall (401, 402) gets no snippet: that content is not public (brief: no paid databases). Nor does a page robots.txt disallows: the site opted out of crawlers, so we do not use a search engine's copy either (stricter reading of the approval, which named 403 blocks; flip `_REFUSALS[safefetch.Disallowed]` in `websearch.py` to change it). It counts for its side like a page of the same type but never makes the strength "silna". A 404/410 or a redirect off the allowlist gets no snippet.
